# DNS Zone Transfer

DNS Zone Transfer (AXFR) is a technique used to replicate DNS zone information between authoritative DNS servers. If a DNS server is misconfigured and allows zone transfers from any host, an attacker can retrieve the entire DNS database for a domain, revealing valuable information such as subdomains, internal hosts, mail servers, and name servers.

Misconfigured zone transfers are uncommon in modern environments but are still occasionally found during penetration tests and CTFs. They are also covered in the **INE eJPT** learning path and may appear during the exam.

---

# What is a Zone Transfer?

A DNS zone contains all DNS records for a domain.

Example:

```
target.com
```

The DNS server stores records such as:

```
www.target.com

mail.target.com

vpn.target.com

dev.target.com

ns1.target.com
```

Normally, only secondary DNS servers are allowed to request a full copy of the zone.

A misconfigured server allows **anyone** to request it.

---

# AXFR

Zone transfers use the **AXFR** query type.

```
AXFR = Authoritative Zone Transfer
```

If successful, the attacker receives the complete DNS database.

---

# Why It Matters

A successful zone transfer may reveal:

- Internal hostnames
- Development servers
- VPN gateways
- Mail servers
- Backup servers
- Hidden subdomains
- Network structure
- IP addresses
- Internal naming conventions

This information significantly improves reconnaissance.

# DNS Record Types

Common DNS records include:

| Record | Description |
|----------|-------------|
| A | IPv4 Address |
| AAAA | IPv6 Address |
| MX | Mail Server |
| NS | Name Server |
| TXT | Text Record |
| CNAME | Alias |
| SOA | Start of Authority |
| PTR | Reverse Lookup |

# Discover Name Servers

Before attempting a zone transfer, identify the authoritative name servers.

Using **dig**:

```bash
dig NS target.com
```

Example:

```
ns1.target.com

ns2.target.com
```

Using **host**:

```bash
host -t ns target.com
```

---

# Perform a Zone Transfer

Basic syntax:

```bash
dig AXFR target.com @ns1.target.com
```

or

```bash
dig axfr target.com @ns1.target.com
```

Example:

```bash
dig axfr example.com @ns1.example.com
```

---

# Successful Zone Transfer

Example output:

```
target.com.

www.target.com.

mail.target.com.

vpn.target.com.

dev.target.com.

admin.target.com.

backup.target.com.

ns1.target.com.

ns2.target.com.
```

This indicates that the DNS server is vulnerable.

---

# Failed Zone Transfer

Typical response:

```
Transfer failed.
```

or

```
REFUSED
```

or

```
connection timed out
```

This means the server correctly restricts AXFR requests.

---

# Using host

The **host** command also supports zone transfers.

```bash
host -l target.com ns1.target.com
```

Example:

```bash
host -l example.com ns1.example.com
```

---

# Using dnsrecon

DNSRecon automates DNS enumeration.

Basic scan:

```bash
dnsrecon -d target.com
```

Attempt a zone transfer:

```bash
dnsrecon \
-d target.com \
-t axfr
```

---

# Using Fierce

Another DNS enumeration tool:

```bash
fierce --domain target.com
```

Fierce automatically checks for:

- Zone transfers
- Subdomains
- Name servers

---

# Using Nmap

Nmap includes a DNS zone transfer script.

```bash
nmap \
--script dns-zone-transfer \
-p 53 \
TARGET
```

Example:

```bash
nmap \
--script dns-zone-transfer \
-p 53 \
192.168.1.20
```

# DNS Enumeration Workflow

A typical workflow:

1. Identify the domain.
2. Discover the authoritative name servers.
3. Attempt an AXFR request against each server.
4. Enumerate discovered hosts.
5. Scan new systems with Nmap.
6. Continue web and service enumeration.

# Why Zone Transfers Are Dangerous

A successful transfer may expose:

```

intranet.target.com

git.target.com

```

Many of these hosts are never publicly linked.

# Common Mistakes

Avoid these mistakes:

- Attempting AXFR before identifying the authoritative name servers.
- Testing only one DNS server.
- Ignoring discovered subdomains.
- Failing to scan newly discovered hosts.
- Forgetting to enumerate MX and TXT records.
- Assuming a failed AXFR means no DNS information can be gathered.

---

# eJPT Tips

During the **INE eJPT** exam:

- Always enumerate DNS when a domain name is provided.
- Identify all authoritative name servers before attempting a zone transfer.
- Try AXFR against every available name server.
- Scan any newly discovered hosts with **Nmap**.
- Follow up with web, SMB, FTP, SSH, or SNMP enumeration where appropriate.
- Combine DNS reconnaissance with **Gobuster**, **Wfuzz**, and **Nmap** to build a complete picture of the target.

# Summary

DNS Zone Transfer (AXFR) is a valuable reconnaissance technique that can reveal an organization's entire DNS zone if the DNS server is improperly configured. Although modern servers typically restrict zone transfers to authorized secondary name servers, testing for AXFR remains a quick and effective step during information gathering. A successful transfer can expose hidden systems, internal naming conventions, and additional attack surfaces, making it an important technique to understand for both real-world engagements and the **INE eJPT** exam.
